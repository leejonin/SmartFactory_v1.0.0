## 1. 개요·목적·범위

기존 한 레이어와 동일한 기본 구성을 세 개 더 추가하여 총 네 레이어로 확장한다. 레이어별로 별도 운영 규칙을 새로 만들지 않는다. 이번 문서는 대화에서 정정·확인한 기본 단위와 수량, 목적지 표, 확장 수행 순서 및 확인 기준을 담는 에이전트 전달용 추가 계획문서다.

**목적:** 스마트팩토리 웹 3D 장면에서 기존 물류 처리 단위를 반복 배치하여, 네 레이어의 상자 이송·QR 인식·AGV 운반·출하 구성을 표현한다.

**목표:** 기존 1개에 같은 기본 형식의 레이어 3개를 추가하고, 4절 수량과 5절 목적지 대응이 실제 장면에서 일치하는지 확인한다.

사용자가 별도 프로젝트 문서에 작성해 두었다고 밝힌 AGV 혼잡·대기 위치·운영 규칙은 이번 문서에 다시 작성하지 않는다. 해당 문서를 열람한 것으로 주장하거나 세부 내용을 추정하지 않는다. 이번 작성은 계획 제출이며 실제 소스·씬·장비를 수정하는 작업은 아니다.

## 3. 레이어 기본 구성과 확장 관계

```text
ExistingLayerCount := 1
AddedLayerCount := 3
L := {L1,L2,L3,L4}
count(L) = ExistingLayerCount + AddedLayerCount = 4

forall l in L,
    count(I(l)) = 4
    count(C(l)) = 1
    count(Q(l)) = 1
    count(A(l)) = N
    count(D(l)) = 3
    count(T(l)) = 3

BasicStructure(L1) = BasicStructure(L2)
BasicStructure(L2) = BasicStructure(L3)
BasicStructure(L3) = BasicStructure(L4)
```

`L1`은 기존 레이어, `L2..L4`는 추가 레이어를 구분하는 문서 내 표지이며 정식 기능 ID가 아니다. `BasicStructure`는 수량과 역할·연결의 기본 형식이다. 목적지 이름이 다르더라도 레이어별로 다른 운영 규칙을 부여한다는 의미는 아니다.

`Connect(x,y)`는 상자 이송이 연결됨, `End(c)`는 컨베이어 c의 끝, `Location(q)`는 스캐너 q의 위치다. `c`와 `q`는 각각 해당 레이어의 유일한 중앙 컨베이어와 QR 스캐너다.

```text
forall l in L,
    forall i in I(l), Connect(i,c) = true, where c in C(l)
    Location(q) = End(c), where q in Q(l), c in C(l)
    Flow(l) := [네입구, 중앙컨베이어, 끝QR인식, AGV인수, 목적지출하도크, 해당탑차]
```

`Flow(l)`는 해당 레이어의 처리 순서다. 네 입구가 중앙 컨베이어로 이어지고 끝에서 QR을 읽은 뒤, AGV가 해당 출하 도크의 탑차로 물류를 이송한다. 상자를 실제로 싣고 내리는 장치 방식이나 별도 운영 규칙은 이번 문서에서 새로 정하지 않는다.

## 4. 레이어별 구성 수량

| 레이어 | 입구 | 중앙 컨베이어 | QR 스캐너 | AGV | 출하 도크 | 탑차 |
|---|---:|---:|---:|---:|---:|---:|
| 1 — 기존 | 4개 | 1개 | 1개 | N대 | 3곳 | 3대 |
| 2 — 추가 | 4개 | 1개 | 1개 | N대 | 3곳 | 3대 |
| 3 — 추가 | 4개 | 1개 | 1개 | N대 | 3곳 | 3대 |
| 4 — 추가 | 4개 | 1개 | 1개 | N대 | 3곳 | 3대 |
| 합계 | 16개 | 4개 | 4개 | 4N대 | 12곳 | 12대 |

```text
sum(l in L) count(I(l)) = 4 * 4 = 16
sum(l in L) count(C(l)) = 4 * 1 = 4
sum(l in L) count(Q(l)) = 4 * 1 = 4
sum(l in L) count(A(l)) = 4 * N
sum(l in L) count(D(l)) = 4 * 3 = 12
sum(l in L) count(T(l)) = 4 * 3 = 12
AddedTruckCount := 3 * 3 = 9
AddedDockCount := 3 * 3 = 9
```

AGV 합계 4N대는 네 레이어에 같은 N대를 적용하는 기준이다. N의 실제 값은 사용자가 별도 관리하는 프로젝트 설정을 따른다. 이번 문서에서 새 숫자를 지정하지 않는다. 각 레이어는 도크 세 곳과 탑차 세 대를 각각 갖는다.

## 5. 출하 도크·탑차 목적지 표

| 레이어 | 도크 1 · 탑차 목적지 | 도크 2 · 탑차 목적지 | 도크 3 · 탑차 목적지 | 근거 상태 |
|---|---|---|---|---|
| 1 — 기존 | 목동 | 합정동 | 면목동 | 기존 사용자 지정 |
| 2 — 추가 | 역삼동 | 잠실동 | 천호동 | 앞서 제시한 추가 배정안 |
| 3 — 추가 | 화곡동 | 구로동 | 독산동 | 앞서 제시한 추가 배정안 |
| 4 — 추가 | 상계동 | 창동 | 길음동 | 앞서 제시한 추가 배정안 |

사용자가 표를 추가 확장 계획문서로 제출하라고 요청하여 위 배정안을 문서에 포함한다. 지역 추천은 시뮬레이션 구성용이며 실제 배송량·거리·도로망을 최적화해 산출한 결과가 아니다.

`R(l)`은 해당 레이어에서 처리하는 목적지 목록, `j`는 1~3의 도크·탑차 번호다. `d(l,j)`와 `t(l,j)`는 레이어 l의 j번째 도크와 탑차, `Dest(x)`는 대상 x의 목적지다. `b`는 레이어 l에서 생성되는 상자, `Pick`은 목록에서 한 목적지를 랜덤 선택하는 개념 처리다.

```text
R(L1) := [목동, 합정동, 면목동]
R(L2) := [역삼동, 잠실동, 천호동]
R(L3) := [화곡동, 구로동, 독산동]
R(L4) := [상계동, 창동, 길음동]

forall l in L, forall j in {1,2,3},
    Dest(d(l,j)) = Dest(t(l,j)) = R(l)[j]

OnCreate(b,l) => Dest(b) := Pick(R(l))
QRPayload(b) := Dest(b)
ReadOK(b,l) = true and ReadDest(b) = R(l)[j]
    => TargetDock(b) := d(l,j)
```

`OnCreate`는 상자 생성 시점, `QRPayload`는 QR에 담는 목적지, `ReadOK`는 QR 판독 성공, `ReadDest`는 판독한 목적지, `TargetDock`은 이송 대상 도크다. 기존 랜덤 목적지 배정 방식에 각 레이어의 목적지 목록을 연결한다. 목적지 외 QR 필드를 임의로 추가하지 않는다. 인식 실패 처리·AGV 운용 세부사항은 별도 프로젝트 문서의 규칙을 따르며 이 문서에서 재작성하지 않는다.

## 7. 수행 순서

`S`는 수행할 단계의 순서열, `k`는 1~5의 단계 번호다. `Done(k)`는 실제 수행과 단계별 확인을 마친 상태다.

```text
S := [기존구성확인, 세레이어추가, 도크탑차수량확인, 목적지QR연결, 전체검증]
forall k in {2,3,4,5}, Start(k) => Done(k-1) = true
forall k in {1,2,3,4,5}, Status(Done(k)) := 실행 미확인
```

| 단계 | 예정 작업 | 확인할 내용 |
|---|---|---|
| 1 | 기존 레이어의 실제 구성·소스·설정을 확인 | 3절 기본 단위와 기존 기능 ID·대상 파일의 대응 |
| 2 | 같은 기본 구성의 레이어 세 개를 추가 | 총 네 레이어, 각 입구 4개·중앙 컨베이어 1개·QR 1개·AGV N대 |
| 3 | 추가 레이어마다 출하 도크와 탑차를 배치 | 도크 9곳·탑차 9대를 추가하여 각각 총 12곳·12대 |
| 4 | 5절 표대로 레이어별 목적지와 QR·도크·탑차를 연결 | 상자 목적지와 판독값, 도크·탑차 목적지 일치 |
| 5 | 네 레이어의 기본 흐름과 수량을 확인 | 아래 완료 기준과 대조 |

공간 배치 좌표·복사 간격·추가 카메라·새 UI·새 운영 규칙은 이번 요청에서 정하지 않았다. 구현 범위를 채운다는 이유로 새 기능을 추가하지 않는다.

## 8. 확인 방법·완료 기준

| 확인 대상 | 예정 확인 방법 | 완료 기준 |
|---|---|---|
| 전체 수량 | 레이어별 객체 구성과 합계를 확인 | 4절 표와 일치 |
| 레이어 형식 | 각 레이어의 구성과 연결을 대조 | 동일 기본 형식의 4개 세트 |
| 목적지 | 도크·탑차 설정값을 확인 | 5절 표와 대응 |
| QR 이송 | 각 레이어에서 목적지 세 종류의 상자로 흐름 확인 | QR 판독 목적지와 해당 도크·탑차가 일치 |
| 기록 | 실제 변경 파일과 실행 결과를 확인 | 해당 기능 ID의 day에 기록하고 이 계획과 연결 |

`V`는 위 확인 항목의 집합, `Result(v)`는 항목 v의 실제 검증 결과다. `ExtensionComplete`는 추가 확장을 실행·검증한 완료 상태다.

```text
V := {전체수량, 레이어형식, 목적지대응, QR이송, 작업기록}
forall v in V, Result(v) := 실행 미확인
ExtensionComplete := forall v in V, Result(v) = 통과
Status(계획문서본문) := 작성 완료
Status(추가확장구현) := 이번 작업에서 미수행
```

확인 항목의 정의는 구현 성공을 의미하지 않는다. 이번 작업에서는 문서 본문과 수량 계산·표의 일치만 검토했으며 프로그램을 실행하지 않았다.

참조표지는 문서 내 항목 구분용이며 정식 기능·문제 ID를 대신하지 않는다. 실행환경·기존 중분류·번호 목록을 모르므로 정식 ID를 임의로 확정하지 않는다. 근거 있는 프로그램 버그·에러 기록은 없음이며, 미실행을 무결함 판정으로 해석하지 않는다.

### v0.0.1 전달 대상 명시

사용자 추가 지시에 따라 전달 대상을 개발 에이전트로 명시했다. 구성·수량·목적지·순서·완료 조건의 텍스트 수식과 각 기호의 정의를 유지했다. 사용자용 이미지가 에이전트용 조건 정의를 대신하지 않는다.

## 구현 결과 및 사용자 정정

한 공장 바닥에 L1~L4 물류 라인을 위에서 아래로 1열 배치한다. 각 원점은 X=0, Z=0·29·58·87이다. 이전 40m 간격을 29m로 줄이고 공장 깊이를 160m에서 120m로 줄였다. AGV 복귀 통로와 각 라인의 독립 운행은 유지한다.

총 유입구 16개, QR 4개, 도크·탑차 각각 12개다. 레이어당 AGV N=1~3대를 동일 적용하며 기본 3대, 전체 12대다. AGV 속도는 1.2m/s이며 선배차·QR 옆 대기·직행 복귀·병렬 구간 예약을 유지한다.

L1: 목동·합정동·면목동. L2: 역삼동·잠실동·천호동. L3: 화곡동·구로동·독산동. L4: 상계동·창동·길음동.

FactorySimulation은 같은 Simulation을 네 번 생성한다. step/reset/setAgvCount/retryScan은 네 인스턴스에 적용한다. boxes/agvs/delivered는 전체 상태를 모으고 lastRead는 가장 최근 판독, events는 최근 8개 기록을 레이어 이름과 함께 반환한다. Simulation의 regions와 decodeRegion의 허용 지역을 레이어별로 전달해 다른 라인의 목적지를 거절한다. layout.js가 위치와 지역의 단일 설정 원본이다.

createScene은 하나의 바닥·외벽·렌더러 아래 buildLayer로 네 장면 그룹을 배치한다. GLB는 URL별로 한 번 로드하고 트럭 병합 결과를 공유한다. 카메라는 전체 1열 범위에 맞췄으며 QR·AGV 근접 뷰는 L1 기준이다.

검증: npm test 13개 통과, npm run build 통과. 4라인 10분 고정 시드 검사에서 도크별 인도 [5,13,14,9,15,9,14,8,8,7,9,15], 모든 도크 출하·물량 보존·레이어 독립성 및 검사한 세계 좌표에서 AGV 충돌 없음. 브라우저에서 16/16 장비 배치, 1열 공용 바닥, 축소 간격, 12개 목적지·AGV 표시 확인. 기존 JS 번들 크기 경고(약820kB)는 남음. 실제 현장 성능과 저사양 GPU는 미확인.
